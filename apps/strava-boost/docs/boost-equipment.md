# Trace 장비·정비

`boost`는 개발 중 사용하는 약칭이며, 화면의 서비스 이름과 좌측 상단 로고는 Trace다.

## 화면과 이동

- `/`: 기존 라이딩 통계 홈. 상단 **내 장비·정비** 메뉴로 작업대에 이동한다.
- `/equipment`: **정비 현황 / 내 장비 / 라이딩별 조합**. 상단 **라이딩 통계** 메뉴와 Trace 로고로 홈에 돌아간다.
- `/activity/:id`: 기존 경로·고도 프로필. `/statistics`는 호환성을 위해 홈으로 이동한다.
- `/demo`: 자전거 3대와 예시 부품으로 조작을 시험한다. 로그인한 브라우저에서도 API를 호출하거나 기록을 영구 저장하지 않는다.

## 부품과 사용 기록

- 같은 모델의 타이어도 각각 등록해 다른 ID·추적 시작일·기존 사용 거리를 가진다.
- 휠셋, 앞/뒤 타이어, 체인, 스프라켓, 앞/뒤 브레이크를 배정한다.
- 데스크톱에서는 보관함의 부품을 끌어 놓거나 선택한다. 모바일에서는 장착 위치를 누르면 하단 선택창이 열린다. 버튼을 통한 키보드 선택도 지원한다.
- 장착 변경은 일시가 있는 이력으로 추가하며, 늦게 업로드한 라이딩도 실제 시작 시점의 조합을 사용한다.
- 라이딩별로 확정한 조합이 장착 이력보다 우선한다. 현재 조합·빠른 조합·Strava 자전거가 바뀌어도 확정 기록을 유지한다.
- 한 실물 부품을 앞뒤 또는 두 자전거에 동시에 장착할 수 없다. 이동할 때는 먼저 분리하고 새 자전거에 장착한다.
- 거리는 최신 활동에서 다시 계산한다. 재동기화나 거리 수정으로 중복 가산하지 않는다. 실내 트레이너는 체인·스프라켓만 계산한다.
- 부품 상세에서 누적 거리와 자전거별 장착 기간을 확인한다. 보관 중인 기간은 장착 일수에서 제외한다.
- Strava에 쓰기 작업은 하지 않는다. 동기화한 라이딩의 자전거 ID와 연결하며, 부품 조합은 Trace 내부에만 기록한다.

## 정비

부품 또는 자전거에 거리/기간 주기를 지정하고 마지막 정비 일시와 메모를 기록한다.
둘 중 먼저 도달하는 기준으로 **여유 있음 / 곧 정비 / 정비 기준 도달**을 표시한다.
마지막 정비일을 모르면 **이전 정비일 필요**로 표시하며 임의로 추정하지 않는다.
정비 기록 추가·삭제 시 정비 후 거리·기간만 다시 계산하고 부품의 전체 누적 거리는 유지한다.
현재 알림은 앱 안의 상태 표시다. 웹 푸시·이메일·앱을 닫은 동안의 알림과 부품 이미지 등록은 후속 범위다.

## 저장과 적용

기존 Strava 로그인과 공유 DB의 `strava_boost.activities`를 그대로 사용한다.
새 OAuth 흐름이나 Supabase 회원 가입, 추가 환경변수는 도입하지 않는다.

운영 적용 전 **plan-my-route Supabase 프로젝트의 SQL Editor**에서 다음 파일을 한 번 실행한다.

`supabase/migrations/20261026_add_equipment_maintenance.sql`

이미 실행한 `20261025_add_shared_database.sql`은 다시 실행할 필요가 없다.
새 프로젝트에는 `supabase/schema.sql`을 사용한다. `strava_boost`는 이미 노출된 스키마이므로 Exposed schemas 변경도 필요 없다.
새 마이그레이션에는 스키마 캐시 재로드 알림이 포함된다.

- `strava_boost.garages`: 사용자별 자전거·부품·장착·라이딩 배정·프리셋·정비 문서를 원자적으로 저장한다.
- `strava_boost.save_garage`: revision이 일치할 때만 갱신한다. 다른 기기에서 먼저 저장했으면 409를 반환하며 입력 초안과 대화상자를 유지한다.
- 모든 접근은 서버가 Strava에서 확인한 사용자 ID로 제한한다. 라이딩 배정은 해당 사용자가 동기화한 활동인지 확인하고 부품 수명도 검증한다.
- RLS 활성화, anon/authenticated 차단, service_role의 SELECT/INSERT/UPDATE 및 함수 EXECUTE만 명시적으로 부여한다.
- 기존 public/auth/next_auth 객체·설정·회원 계정과 기존 활동·동기화 시각은 변경하지 않는다. 프로젝트의 서버 키가 가진 전체 권한 범위는 기존과 같다.

## 파일 배치

페이지 전용 코드는 가까운 라우트의 `_components`, `_hooks`, `_lib`에 둔다.

- `app/(statistics)/`: 기존 통계 홈과 전용 코드. 라우트 그룹이므로 홈 URL은 `/`다.
- `app/(boost)/_components`, `_lib`: 장비 화면과 데모가 공유하는 UI·날짜 입력·API 클라이언트.
- `app/(boost)/demo/_lib`: 예시 데이터.
- `app/activity/[id]/_components`, `_lib`: 라이딩 상세 지도·프로필·전용 타입.
- `app/_components/SiteNavigation.tsx`: 통계와 장비의 공통 이동 메뉴.
- `lib/equipment.ts`: 화면과 API가 공유하는 계산·검증 모델.
- `lib/server/strava-session.ts`: 기존 활동 저장 API와 장비 API가 공유하는 Strava 사용자 검증.

## 검증

- 단위/API 테스트 55개, plan-my-route 회귀 테스트 83개 통과. 기존 공유 DB·웹훅·개별 재동기화 회귀 테스트 포함.
- 타입 검사와 Next.js 16.4.3 webpack 프로덕션 빌드 통과.
- 임시 PostgreSQL 호환 DB에서 새 SQL 적용/재실행, 초기 스키마 일치, 기존 활동·동기화/plan-my-route 객체·권한·정책 보존 확인.
- DB 함수의 오래된 revision 거절과 기존 내용 유지, 사용자별 문서, 최소 권한 확인.
- 브라우저: 드래그 배정, 모바일 선택창, 부품 등록, 라이딩별 확정 후 현재 조합 변경, 정비 카운터 초기화와 누적 거리 유지 확인.
- 독립 브라우저 2개와 모킹한 공유 API로 홈↔장비 이동, 이동 후 데이터 유지, 저장 충돌과 초안 유지 확인.
- 320/375/768/1440px 가로 넘침 없음, Esc 닫기, 로그인한 상태에서 데모 API 요청 0건 확인.

장비 마이그레이션은 운영 DB에 아직 실행하지 않았다. 실제 장비 저장은 SQL 적용 후 확인해야 한다.
